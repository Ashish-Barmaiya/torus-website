# Quick Start

This guide configures a minimal Torus instance, starts the proxy, and forwards the first request to two backend servers.

By the end of this page you will have a working reverse proxy using round-robin load balancing.

---

## Start two backend servers

If you have not already done so, start the included mock backend twice.

Terminal 1

```bash
go run ./cmd/mock-backend 3001
```

Terminal 2

```bash
go run ./cmd/mock-backend 3002
```

Each backend responds with its listening port, making it easy to observe load balancing.

---

## Create a configuration

Create a file named `torus.yaml`.

```yaml
apiVersion: v2

server:
  addr: ":8080"

health:
  interval_ms: 5000
  timeout_ms: 2000
  path: /health

services:
  - name: api
    upstreams:
      - http://localhost:3001
      - http://localhost:3002

routes:
  - path: /api
    service: api
```

This configuration defines:

- an HTTP listener on port `8080`
- a health checker
- one service with two upstream backends
- one route (`/api`) that selects that service

---

## Start Torus

Run the proxy.

```bash
./torus -config torus.yaml
```

The proxy begins listening on:

```text
http://localhost:8080
```

---

## Verify readiness

Open another terminal.

```bash
curl http://localhost:8080/readyz
```

Expected response:

```text
ok
```

The readiness endpoint indicates that Torus has successfully initialized and is ready to accept traffic.

---

## Send requests

Forward several requests through the proxy.

```bash
curl http://localhost:8080/api/hello
```

Run the command multiple times.

Because the configuration contains two healthy upstreams, responses should alternate between the backend running on port `3001` and the backend running on port `3002`.

Example:

```text
Backend :3001
```

```text
Backend :3002
```

```text
Backend :3001
```

```text
Backend :3002
```

This demonstrates Torus' round-robin load balancer.

---

## What happened?

Every request forwarded through Torus follows the same deterministic execution pipeline.

<RequestFlow
  steps={[
    "Client",
    "HTTP Listener",
    "Runtime Snapshot",
    "Router",
    "Service",
    "Load Balancer",
    "Reverse Proxy",
    "Backend",
  ]}
/>

Each stage has a single responsibility:

1. **HTTP Listener** accepts the incoming connection.
2. **Runtime Snapshot** provides an immutable view of the active configuration.
3. **Router** matches the request using longest-prefix routing.
4. **Service** resolves the logical destination.
5. **Load Balancer** selects a healthy upstream.
6. **Reverse Proxy** forwards the request and streams the response.
7. **Backend** processes the request and returns the response.

The complete execution pipeline, runtime model, and configuration reload mechanism are described in the **Architecture** documentation.
