# Observability

Operating a reverse proxy requires visibility into its runtime behavior.

Torus provides built-in observability features that help operators understand traffic flow, backend availability, runtime health, and operational events without modifying application code.

The observability subsystem is designed around three complementary signals:

- **Metrics** measure the current and historical behavior of the proxy.
- **Logs** record operational events and individual requests.
- **Health endpoints** expose readiness information for orchestration platforms and load balancers.

Together, these signals provide a complete operational view of a running Torus instance.

---

## Observability architecture

```text
                    Torus
                      │
      ┌───────────────┼───────────────┐
      ↓               ↓               ↓
  Metrics         Request Logs    Health Endpoint
      ↓              ↓               ↓
 Prometheus      stdout / journald   /readyz
      ↓
  Grafana
```

Each signal serves a different operational purpose and should be monitored together.

---

## Metrics

Metrics expose numerical measurements describing the current state of the proxy.

Examples include:

- request throughput
- response latency
- backend availability
- runtime state
- reload activity

Metrics are intended for continuous collection by monitoring systems such as Prometheus.

---

## Logging

Logs provide an event-oriented record of proxy activity.

Request logs capture:

- incoming requests
- selected routes
- upstream targets
- response status
- processing duration

Operational logs record events such as startup, shutdown, configuration reloads, and runtime errors.

---

## Health endpoint

Torus exposes a readiness endpoint for external systems.

```text
GET /readyz
```

The endpoint reports whether Torus has completed initialization and is ready to receive traffic.

Load balancers, container orchestrators, and monitoring systems use this endpoint to determine service availability.

---

## Operational workflow

A typical production monitoring pipeline looks like:

```text
            Torus
              │
     ┌────────┴────────┐
     ▼                 ▼
 Metrics             Logs
     ↓                 ↓
Prometheus      Log Collection
     ↓
 Grafana
```

Health endpoints complement this workflow by providing lightweight availability checks.

---

## Production recommendations

For production deployments:

- enable metrics collection
- retain structured request logs
- monitor the readiness endpoint
- alert on backend health changes
- collect historical performance data
- correlate metrics with logs when investigating incidents
