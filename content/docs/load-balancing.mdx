# Load Balancing

Once the router has selected a service, Torus must choose which backend server will receive the request.

This responsibility belongs to the load balancer.

The load balancer operates on the backend pool owned by a service and selects one healthy backend for every incoming request.

---

## Responsibilities

The load balancer is responsible for:

- selecting an upstream backend
- distributing requests across available backends
- skipping unhealthy backends
- returning the selected backend to the reverse proxy

It does **not** perform request routing or proxy requests.

---

## Current algorithm

Torus currently implements **round-robin load balancing**.

Each request is forwarded to the next healthy backend in the service's backend pool.

Example:

```text
Backend Pool

A
B
C
```

Incoming requests are distributed as:

```text
Request 1 → A
Request 2 → B
Request 3 → C
Request 4 → A
Request 5 → B
Request 6 → C
```

Every healthy backend receives approximately the same number of requests over time.

---

## Health-aware selection

Round-robin considers only **healthy** backends.

Suppose the following backend pool exists.

```text
A ✓
B ✗
C ✓
```

Requests are distributed as:

```text
Request 1 → A
Request 2 → C
Request 3 → A
Request 4 → C
```

Backend **B** is skipped until it becomes healthy again.

This prevents requests from being forwarded to unavailable upstream servers.

## Example

Consider the following configuration.

```yaml
routes:
  - path: /api
    upstream:
      - http://localhost:3001
      - http://localhost:3002
      - http://localhost:3003
```

Successive requests will be forwarded to:

```text
localhost:3001
localhost:3002
localhost:3003
localhost:3001
localhost:3002
localhost:3003
```

provided all backends remain healthy.

---

## Failure behavior

If every backend in the pool is unhealthy, Torus cannot forward the request.

The request fails immediately instead of attempting to contact unavailable servers.

This avoids unnecessary network timeouts and provides predictable failure behavior.

---

## Design rationale

Round-robin was selected because it provides:

- deterministic behavior
- even request distribution
- minimal runtime overhead
- straightforward implementation
- predictable performance characteristics

More advanced balancing strategies may be added in future releases without changing the routing or service layers.

---

## Future work

Potential future algorithms include:

- weighted round robin
- least connections
- least latency
- consistent hashing
- request affinity

These can be introduced while preserving the existing service abstraction.
