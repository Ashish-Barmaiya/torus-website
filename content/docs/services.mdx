# Services

A service represents the logical destination selected by the router.

Routes do not point directly to backend servers. Instead, each route resolves to a service, and the service owns the upstream backend pool responsible for handling the request.

Separating routing from backend management keeps each component focused on a single responsibility.

---

## Responsibilities

A service is responsible for:

- representing a logical application
- owning one or more upstream backends
- exposing a backend pool to the load balancer
- isolating routing from backend implementation

A service does **not** perform request matching or proxy requests.

---

## Why services exist

Consider the following configuration.

```yaml
routes:
  - path: /api
    service: api

  - path: /admin
    service: admin
```

Each route identifies **what** should handle the request.

The service then determines **where** that request should be forwarded.

This separation allows routing logic and backend management to evolve independently.

---

## Relationship to routing

The router selects a service using longest-prefix matching.

<RequestFlow steps={["Incoming Request", "Router", "Selected Service"]} />

At this stage, no backend has been chosen.

Backend selection occurs later through the load balancer.

---

## Relationship to load balancing

Every service owns an upstream backend pool.

For example:

```
Service: api

├── Backend A
├── Backend B
└── Backend C
```

The load balancer selects one healthy backend from this pool for each request.

Different services maintain independent backend pools.

## Benefits

Using a dedicated service layer provides several advantages.

### Separation of concerns

Routing determines **which service** should receive a request.

Services determine **which backend pool** belongs to that route.

---

### Independent backend management

Backend health, load balancing, and future routing policies remain isolated from the routing subsystem.

---

### Better extensibility

Additional capabilities such as weighted load balancing, canary deployments, or traffic shaping can be implemented at the service layer without modifying the router.

---

## Example

Suppose the following services exist.

```text
api
├── 10.0.0.11
├── 10.0.0.12
└── 10.0.0.13

admin
├── 10.0.1.21
└── 10.0.1.22
```

Requests to:

```text
/api/users
```

always resolve to the **api** service.

Requests to:

```text
/admin
```

always resolve to the **admin** service.

The router never needs to know how many backend servers each service contains.

---

## Design rationale

Introducing a service layer keeps the execution pipeline modular.

Each subsystem performs exactly one task.

This architecture reduces coupling and makes the request pipeline easier to reason about, test, and extend.
