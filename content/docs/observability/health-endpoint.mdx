# Health Endpoint

Torus exposes a lightweight readiness endpoint that reports whether the proxy is ready to receive client traffic.

Unlike active health checks, which continuously monitor upstream backends, the health endpoint reports the operational state of the Torus process itself.

It is intended for automated systems such as load balancers, container orchestrators, deployment pipelines, and monitoring tools.

---

## Endpoint

```text
GET /readyz
```

The endpoint always returns a simple plain-text response.

| Status                    | Response    |
| ------------------------- | ----------- |
| `200 OK`                  | `ready`     |
| `503 Service Unavailable` | `not ready` |

---

## Purpose

The endpoint answers a single question:

> **Can this Torus instance safely receive new requests?**

External systems can use this endpoint before routing traffic to the proxy.

Unlike application requests, readiness probes are inexpensive and do not involve routing or proxying to upstream services.

---

## Readiness state

Internally, Torus maintains a simple readiness state.

```text
Process Starts
       ↓
Build Runtime
       ↓
Start HTTP Server
       ↓
ready = true
```

During shutdown, Torus marks itself as unavailable before terminating.

```text
Shutdown Begins
       ↓
ready = false
       ↓
Graceful Shutdown
       ↓
Process Exit
```

This allows external systems to stop sending new traffic while existing requests complete.

---

## Health endpoint vs backend health checks

Although their names are similar, they serve different purposes.

| Health Endpoint                             | Backend Health Checks                         |
| ------------------------------------------- | --------------------------------------------- |
| Reports whether the Torus process is ready. | Reports whether upstream servers are healthy. |
| Intended for external systems.              | Used internally by the load balancer.         |
| One endpoint for the proxy.                 | One health state per backend.                 |

A healthy Torus instance may still have unhealthy upstreams.

Likewise, healthy upstreams are irrelevant if the proxy itself is not ready to accept requests.

---

## Typical deployment

```text
                 Load Balancer
                       │
          GET /readyz every few seconds
                       ↓
                     Torus
```

Only instances reporting `200 OK` should receive new traffic.

---

## Design characteristics

The readiness endpoint is intentionally simple.

- lightweight HTTP handler
- constant-time response
- no backend communication
- safe for frequent polling
- independent of request traffic

Its purpose is to expose the state of the proxy itself, not the applications behind it.
