# Logging

Torus emits structured JSON logs describing both client requests and internal runtime events.

Logs record individual events as they occur. Together, they provide a complete picture of the behavior of a running proxy.

Logs are written to standard output and are intended to be consumed directly during development or collected by external logging systems in production.

---

## Logging philosophy

The logging system follows several design principles.

- Structured JSON output.
- Human-readable event names.
- Consistent field names.
- Minimal logging overhead.
- High-value operational events.
- Avoid unnecessary log noise.

For example, successful health checks are intentionally **not** logged. Only failures are recorded.

---

## Log categories

Torus currently produces two categories of logs.

### Request logs

A request log is emitted after every HTTP request processed by the proxy.

Each entry includes:

- HTTP method
- request path
- response status
- request duration
- client address
- request identifier

Example:

```json
{
  "time": "2026-08-07T16:21:44Z",
  "level": "INFO",
  "msg": "request",
  "method": "GET",
  "path": "/api/hello",
  "status": 200,
  "duration_ms": 2,
  "request_id": "71f7866d-d674-4299-9a83-2ccf684eca24",
  "client_ip": "[::1]:59255"
}
```

These logs provide a chronological record of traffic flowing through the proxy.

---

### Operational logs

Operational logs describe events occurring within Torus itself.

Examples include:

- server startup
- TLS initialization
- configuration watcher startup
- runtime creation
- configuration reloads
- runtime retirement
- health check failures
- configuration validation failures
- graceful shutdown

These events provide visibility into the internal behaviour of the proxy independently of client traffic.

---

## Log levels

Torus currently emits three log levels.

| Level     | Purpose                                                                                                       |
| --------- | ------------------------------------------------------------------------------------------------------------- |
| **INFO**  | Normal operational events and request logs.                                                                   |
| **WARN**  | Recoverable conditions that may require operator attention, such as failed backend health checks.             |
| **ERROR** | Failures that prevent an operation from completing successfully, such as invalid configuration during reload. |

---

## Startup logging

During startup Torus records the initialization sequence.

Typical events include:

- TLS configuration loaded
- configuration watcher started
- runtime started
- server listening

For example:

```json
{
  "level": "INFO",
  "msg": "runtime started",
  "generation": 1
}
```

These logs confirm that the proxy has successfully initialized and is ready to receive traffic.

---

## Runtime reload logging

Every successful configuration reload generates operational events describing the transition between runtime generations.

Typical events include:

- configuration loaded
- runtime reloaded
- previous runtime retired

Example:

```json
{
  "level": "INFO",
  "msg": "runtime reloaded",
  "old_generation": 2,
  "new_generation": 3
}
```

If configuration parsing or validation fails, Torus logs the error and continues serving traffic using the existing runtime.

Example:

```json
{
  "level": "ERROR",
  "msg": "failed to reload configuration",
  "error": "routes[0].upstream[2]: missing port"
}
```

---

## Health check logging

Health checks execute continuously in the background.

To avoid excessive log volume, successful probes are not logged.

Only failed health checks generate log entries.

Example:

```json
{
  "level": "WARN",
  "msg": "health check failed",
  "checker": "http://localhost:3002",
  "error": "dial tcp ... connection refused"
}
```

This allows backend failures to be identified immediately without flooding the logs during normal operation.

---

## Request identifiers

Every request processed by Torus carries a request identifier.

If the incoming request already contains an `X-Request-ID` header, Torus preserves it.

Otherwise, a new UUID is generated automatically.

The request identifier is:

- added to the request context
- forwarded as the `X-Request-ID` header
- included in the request log

This makes it possible to correlate requests across multiple services.

---

## Shutdown logging

Graceful shutdown is also fully logged.

Typical events include:

- shutdown signal received
- graceful shutdown initiated
- graceful shutdown completed
- server shutdown complete

These events provide a complete record of the server lifecycle.

---

## Collecting logs

Because logs are written to standard output, Torus integrates naturally with common logging infrastructure, including:

- Docker
- journald
- Kubernetes
- Fluent Bit
- Vector
- Loki
- Elasticsearch

No additional logging configuration is required.
