# Configuration Reload

Torus monitors its configuration file and supports reloads without a process restart. When it detects a change, it reads and validates the candidate configuration and attempts to construct a new runtime generation.

```text
Configuration change
        ↓
Read YAML → Parse → Validate → Build runtime
                                      ↓
                              Atomic runtime swap
                                      ↓
                         New requests use new runtime
```

Only a valid new generation replaces the active runtime.

## Runtime generations

Each accepted configuration creates a runtime generation containing the state required to serve requests: routing, services, upstream pools, backend health state, observability configuration, and other runtime-owned state. The active runtime is immutable after construction.

After an atomic replacement, requests that begin use the new runtime. Existing requests continue according to the runtime lifecycle rules that applied when they began.

## Invalid changes are isolated

A file change is not automatically accepted. Torus must parse, validate, and construct a runtime from it. If any stage fails, the active runtime remains in service.

```text
Configuration change
        ↓
Parse / validate / build fails
        ↓
Keep existing runtime
```

For example, an invalid upstream URL can prevent a candidate generation from becoming active while the previously accepted configuration continues serving traffic.

## Reload or restart?

Use a configuration reload for changes to the YAML configuration. A process restart stops Torus and performs initial runtime construction again, so it is not required merely to apply a valid configuration change.

The deployment model determines the configuration path. For the systemd deployment, the active configuration is installed at `/etc/torus/torus.yaml`.
