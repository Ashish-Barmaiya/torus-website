# Routing

Routing determines which **service** should handle an incoming request.

A route maps a request path to a service:

```yaml
routes:
  - path: /api
    service: api
```

Torus uses longest-prefix matching to select the most specific route that matches the request path.

Routing determines which logical service receives a request. It does not select an individual backend; backends are configured separately under `services`.

---

## Route structure

Each route contains two fields:

| Field     | Required | Description                                         |
| --------- | -------- | --------------------------------------------------- |
| `path`    | Yes      | URL path prefix matched against incoming requests.  |
| `service` | Yes      | Name of the service that handles matching requests. |

```yaml
routes:
  - path: /api
    service: api
```

The referenced service must exist in the `services` section.

```yaml
services:
  - name: api
    upstreams:
      - http://localhost:3001
      - http://localhost:3002

routes:
  - path: /api
    service: api
```

The relationship is:

```text
Request
   ↓
Route
   ↓
Service
   ↓
Upstream Backends
```

See [Services](/docs/configuration/services) for configuring services and their upstream backends.

## Longest-prefix matching

When multiple routes match a request, Torus selects the route with the longest valid prefix.

```yaml
routes:
  - path: /
    service: web

  - path: /api
    service: api

  - path: /api/v1
    service: api-v1
```

A request to `/api/v1/users` matches all three prefixes. The router selects `/api/v1 → api-v1` because `/api/v1` is the longest matching prefix.

| Request         | Selected route | Service  |
| --------------- | -------------- | -------- |
| `/`             | `/`            | `web`    |
| `/about`        | `/`            | `web`    |
| `/api`          | `/api`         | `api`    |
| `/api/users`    | `/api`         | `api`    |
| `/api/v1`       | `/api/v1`      | `api-v1` |
| `/api/v1/users` | `/api/v1`      | `api-v1` |

### Path boundaries

Route matching respects path-segment boundaries.

```yaml
routes:
  - path: /api
    service: api
```

This route matches:

- `/api`
- `/api/`
- `/api/users`
- `/api/v1/users`

It does not match:

- `/apiv1`
- `/api-test`
- `/apix`

A route matches when the request path is exactly the configured path or when the next character after the prefix is `/`. This prevents unrelated paths from matching simply because they begin with the same characters.

## Multiple routes

A configuration can contain multiple routes pointing to different services.

```yaml
routes:
  - path: /api
    service: api

  - path: /admin
    service: admin

  - path: /static
    service: static
```

Each route is evaluated independently during request processing. The router does not need to know which upstream servers belong to each service.

### Root route

A root route can be used as a catch-all route:

```yaml
routes:
  - path: /
    service: web
```

Because `/` is a prefix of every valid request path, it matches requests that do not have a more specific route.

```text
/             → web
/about        → web
/api/users    → api
/admin        → admin
```

More specific routes take precedence over `/`.

## Route and service separation

Routing and backend configuration are intentionally separate.

The route answers: **Which service should handle this request?**

The service answers: **Which backend pool belongs to that service?**

```yaml
services:
  - name: api
    upstreams:
      - http://localhost:3001
      - http://localhost:3002

routes:
  - path: /api
    service: api
```

This separation allows the backend pool of a service to change without changing the route that references it.

---

## Validation

Torus validates routing configuration before constructing a runtime. A route must:

- Define a non-empty path
- Define a service
- Use a unique route path
- Reference a configured service

Invalid routing configuration is rejected before it becomes part of the active runtime. During configuration reload, the existing runtime remains active if validation fails.

### Invalid examples

#### Empty path

```yaml
routes:
  - path: ""
    service: api
```

The route path cannot be empty.

#### Duplicate paths

```yaml
routes:
  - path: /api
    service: api

  - path: /api
    service: admin
```

Route paths must be unique. If different paths need to reach different services, use distinct route prefixes:

```yaml
routes:
  - path: /api
    service: api

  - path: /api/admin
    service: admin
```

#### Unknown service

```yaml
routes:
  - path: /api
    service: payments
```

If `payments` is not defined under `services`, the configuration is invalid.

## Request flow

```text
Incoming Request
       ↓
   Request Path
       ↓
Longest-Prefix Match
       ↓
 Selected Service
       ↓
Service Backend Pool
```

After routing resolves the service, the load balancer selects a healthy backend from that service's upstream pool.

### No matching route

If no configured route matches the request path, Torus does not attempt to contact a backend. The request is rejected with:

```text
404 Not Found
```

For example:

```yaml
routes:
  - path: /api
    service: api
```

A request to `/static/logo.png` does not match the route and is rejected.

---

## Recommended configuration

Keep route definitions explicit and use path prefixes that represent meaningful application boundaries.

```yaml
routes:
  - path: /api
    service: api

  - path: /admin
    service: admin

  - path: /
    service: web
```

Avoid unnecessary overlapping routes. When overlapping routes are intentional, make the hierarchy explicit and rely on longest-prefix matching to determine the destination.
