# Graceful Shutdown

Graceful shutdown allows Torus to terminate safely without abruptly interrupting requests that are already being processed.

When Torus receives a shutdown signal, it immediately stops accepting new traffic while allowing in-flight requests to complete. Only after all active requests have finished does the process exit.

This behavior prevents partially processed requests and minimizes disruption during deployments, maintenance, or system shutdowns.

---

## Shutdown sequence

Every graceful shutdown follows the same sequence.

```text
Shutdown Signal
       ↓
Mark Server Not Ready
       ↓
Stop Accepting New Connections
       ↓
Wait For Active Requests
       ↓
Stop Runtime Workers
       ↓
Exit Process
```

This sequence ensures that new traffic is rejected while existing requests are allowed to finish normally.

---

## Shutdown trigger

Torus performs graceful shutdown when it receives a termination signal from the operating system.

Supported signals include:

- `SIGINT` (Ctrl+C)
- `SIGTERM`

These are the standard signals used by service managers, container runtimes, and orchestration platforms to terminate applications.

---

## Readiness handling

The first action performed during shutdown is marking the server as **not ready**.

The readiness endpoint immediately begins returning:

```text
HTTP/1.1 503 Service Unavailable
```

This allows load balancers and orchestration platforms to stop routing new requests to the instance before the listener is closed.

```text
Shutdown Begins
        ↓
/readyz → 503
        ↓
Traffic Drained
        ↓
Server Stops
```

Existing requests continue executing normally.

---

## Active requests

Requests already being processed are never cancelled immediately.

```text
Request A
──────────────► completes

Shutdown Begins

New Request
──────────────► rejected
```

Every request retains its runtime snapshot until completion.

Only after all active requests have finished does Torus complete the shutdown process.

---

## Shutdown timeout

Graceful shutdown waits for active requests to complete, but only up to a configured timeout.

```text
Shutdown Requested
         ↓
Wait For Active Requests
         │
         ├───────────────┐
         │               │
         ▼               ▼
All Requests Finish   Timeout Expires
         │               │
         ▼               ▼
 Normal Exit      Forced Cancellation
```

This prevents shutdown from blocking indefinitely if requests become stuck.

---

## Forced shutdown

If the graceful shutdown timeout expires before all requests complete, Torus performs a forced shutdown.

Pending request contexts are cancelled and a final shutdown attempt is made before the process exits.

This ensures that shutdown eventually completes even if upstream services become unresponsive.

---

## Runtime cleanup

Graceful shutdown does more than stop the HTTP server.

Once request processing has completed, Torus also stops the active runtime and waits for background workers to exit.

This includes components such as:

- health check workers
- runtime worker groups
- request tracking
- background goroutines owned by the runtime

Shutdown is not considered complete until these resources have been released.

---

## Logging

Shutdown events are recorded as structured log entries.

When shutdown begins:

```json
{
  "level": "INFO",
  "msg": "received shutdown signal"
}
```

```json
{
  "level": "INFO",
  "msg": "Shutting down server",
  "timeout": 25000000000
}
```

After all requests complete successfully:

```json
{
  "level": "INFO",
  "msg": "graceful shutdown complete"
}
```

```json
{
  "level": "INFO",
  "msg": "Server shutdown complete"
}
```

If the shutdown timeout expires, Torus records a warning before cancelling any remaining requests.

```json
{
  "level": "WARN",
  "msg": "graceful shutdown deadline exceeded, forcing cancellation of pending requests"
}
```

If forced shutdown also fails, an error is logged before the process exits.

---

## Design rationale

Graceful shutdown provides several operational benefits.

- prevents interrupted client requests
- allows load balancers to drain traffic safely
- avoids terminating active backend connections
- ensures runtime workers exit cleanly
- releases resources in a predictable order

This behavior is particularly important during rolling deployments and service restarts, where instances are expected to leave service without affecting client traffic.
