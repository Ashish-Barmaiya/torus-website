# Health Checks

Torus continuously monitors every configured backend to determine whether it is capable of serving requests.

This process is known as **active health checking**.

The health subsystem periodically probes each backend and records its availability. The load balancer consults this state before selecting an upstream for a request.

---

## Responsibilities

The health checker is responsible for:

- periodically probing every backend
- tracking backend availability
- marking backends healthy or unhealthy
- exposing health information to the load balancer

It does **not** forward client requests.

---

## Active health probing

Every backend is probed at a configurable interval.

A successful response marks the backend as **healthy**.

A failed probe marks the backend as **unhealthy**.

Only healthy backends are eligible to receive new requests.

## Configuration

A typical health configuration looks like:

```yaml
health:
  interval_ms: 5000
  timeout_ms: 2000
  path: /health
```

| Field         | Description                         |
| ------------- | ----------------------------------- |
| `interval_ms` | Time between probe cycles           |
| `timeout_ms`  | Maximum time to wait for a response |
| `path`        | Endpoint used for health checks     |

---

## Healthy backend

Suppose three backends are configured.

```text
Backend A ✓
Backend B ✓
Backend C ✓
```

The load balancer may choose any of them.

---

## Unhealthy backend

Now suppose Backend B stops responding.

```text
Backend A ✓
Backend B ✗
Backend C ✓
```

New requests are distributed only between:

- Backend A
- Backend C

Backend B remains unavailable until it passes a future health probe.

---

## Recovery

Health status is dynamic.

An unhealthy backend is not permanently removed.

When a later probe succeeds, the backend is automatically returned to the healthy backend pool and becomes eligible to receive traffic again.

No manual intervention is required.

---

## Failure behavior

If every backend becomes unhealthy, Torus cannot safely forward requests.

Rather than attempting connections that are expected to fail, the request is rejected immediately.

This behavior provides predictable failure characteristics and avoids unnecessary upstream connection attempts.

---

## Design rationale

Active health checking provides several advantages.

- Failed backends are removed before client requests reach them.
- Recovery occurs automatically.
- Backend failures are isolated from the routing layer.
- Load balancing decisions remain simple because health state has already been computed.

Keeping health monitoring separate from request forwarding also prevents client traffic from influencing backend availability decisions.

---

## Performance considerations

Health checks execute independently of request processing.

Client requests never wait for a health probe to complete.

Instead, the load balancer reads the current health state that has already been computed by the health subsystem.

This keeps request latency predictable even while backend health is being updated.
