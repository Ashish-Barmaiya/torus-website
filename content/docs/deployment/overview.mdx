# Deployment

Torus supports three deployment models. Configuration defines what Torus does; deployment defines how it is installed and run.

| Model | Intended use |
| --- | --- |
| Native | Local development, debugging, experimentation, and benchmarks. |
| Docker Compose | Reproducible full-stack development, demonstrations, and evaluation. |
| Linux/systemd | Long-running Linux VM operation and the v0.6.0 production-oriented model. |

## Choose a model

Use [Native](/docs/deployment/native) when you need direct host execution. Use [Docker](/docs/deployment/docker) when you want the repository's Torus, mock backends, Prometheus, and Grafana development stack together. Use [systemd](/docs/deployment/systemd) for a managed Linux service.

The Docker Compose files include development-oriented assets such as mock backends, development credentials, and development certificates. They are not a production environment. For a Linux VM, see [Production](/docs/deployment/production).

## Configuration and runtime responsibility

Use [Configuration](/docs/configuration) to create the YAML file that determines the listener, services, routes, health checks, TLS, and observability. Generic examples are in `configs/`; Docker deployments use the deployment-specific assets under `docker/`.

For systemd, responsibilities remain separate:

```text
install.sh → installs and activates the deployment
systemd    → supervises the Torus process
Torus      → owns its runtime and configuration reloads
```

The installer rejects invalid configuration or TLS material before changing the deployment. If installation or activation fails after changes begin, it attempts to restore the preceding deployment. After a successful installation, systemd handles process restarts according to the service policy.
