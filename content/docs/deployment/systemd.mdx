# Linux/systemd Deployment

The repository includes an interactive installer for a native Linux systemd service. It validates the supplied configuration, builds Torus from the source checkout, creates the `torus` user and group when needed, installs the binary and configuration, installs TLS material when configured, enables and starts the service, and verifies the configured listener.

This installer targets Linux with systemd. Docker Compose is the cross-platform container path.

## Prerequisites and configuration

The installer requires Linux, systemd, Go, `curl`, and `ss`; HTTPS deployments also require OpenSSL. It is configuration-driven: it does not ask you to choose HTTP or HTTPS. Run it from the repository root:

```bash
sudo ./deployments/systemd/install.sh
```

Provide a Torus configuration path when prompted. If it contains a `tls` block, provide the source certificate and key paths. The installed configuration should reference the installer-managed paths:

```yaml
tls:
  cert_file: "/etc/torus/tls/cert.pem"
  key_file: "/etc/torus/tls/key.pem"
  min_version: "1.2"
```

The installer validates the certificate, key, and their pairing before installation.

## Installed layout and permissions

```text
/usr/local/bin/torus

/etc/torus/
├── torus.yaml
├── torus.yaml.bak
└── tls/
    ├── cert.pem
    └── key.pem

/etc/systemd/system/torus.service
```

The TLS directory and backup exist only when applicable. The binary is `root:root` with mode `0755`; configuration, TLS files, and the Torus directory are owned by `root:torus` with modes `0640`, `0640`, and `0750` respectively.

## Operate and verify

```bash
sudo systemctl status torus
sudo journalctl -u torus -f
sudo systemctl restart torus
sudo systemctl is-active torus
sudo systemctl is-enabled torus
```

The installer derives the listener from `server.addr`. Verify its actual address after installation:

```bash
curl http://localhost:8080/readyz
```

For HTTPS, use the configured address, such as `curl -k https://localhost:8443/readyz`.

## Metrics, updates, and failures

Enabling `observability.enabled` exposes metrics on Torus's listener, but the installer does not operate Prometheus or Grafana. They are separate components.

The installation flow preserves a configuration backup. A preflight validation failure makes no changes; an installation or activation failure attempts rollback. After a successful install, systemd—not the installer—supervises runtime failures.

Configuration changes follow Torus's reload lifecycle. To upgrade or redeploy the binary, rerun the installer with an explicit maintenance and rollback plan.

## Backup, upgrades, and removal

The installer keeps the prior installed configuration at `/etc/torus/torus.yaml.bak` when applicable. Treat that backup as deployment material: inspect it before a rollback and preserve any separate certificate-management process.

For a new binary or deployment configuration, rerun `sudo ./deployments/systemd/install.sh`. The installer performs its preflight checks before mutating an existing installation and attempts rollback if installation or activation fails.

To remove the managed service, follow the repository uninstall procedure. Stopping and disabling the service alone does not remove the binary, configuration, TLS material, service user, or service definition; review the targets before removing any of those resources.
