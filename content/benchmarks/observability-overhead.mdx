# Benchmark-003: Performance Impact of Observability

> **Status:** Complete

This benchmark measures the runtime cost of enabling Torus observability by comparing otherwise equivalent deployments with observability disabled and enabled under identical benchmark conditions.

## Executive Summary

Enabling observability introduced a **small but measurable runtime cost**.

Under the saturated `wrk` workload, mean throughput decreased by approximately **3.45%**, while average request latency increased by **3.60%**. Under the controlled-rate `Vegeta` workload, throughput remained effectively unchanged and latency increased by only **2–4%** across the reported latency percentiles.

Every benchmark iteration completed successfully, with a **100% request success rate** in both scenarios.

The results indicate that the primary cost of observability is the additional CPU work required to update Prometheus counters, gauges, and histograms during request processing. Resource utilization remained bounded, latency distributions remained consistent across repeated executions, and no evidence of runtime instability or excessive memory growth was observed.

### Principal Findings

- Peak throughput decreased by approximately **3.5%** with observability enabled.
- At **500 requests/sec**, throughput remained effectively unchanged.
- Mean latency increased modestly under both workloads.
- Tail latency remained close to the baseline.
- All requests completed successfully.
- Memory usage remained stable.
- Runtime behaviour remained stable across repeated executions.
- The coefficient of variation for the primary `wrk` throughput measurements remained below **3%**.

## What Was Tested?

The benchmark isolates a single independent variable: the observability configuration.

### Observability Disabled

- Request instrumentation disabled.
- Runtime metrics disabled.
- Backend metrics disabled.
- `/metrics` endpoint unavailable.

### Observability Enabled

- HTTP request metrics enabled.
- Backend metrics enabled.
- Runtime metrics enabled.
- `/metrics` endpoint exposed.
- Prometheus periodically scraped the exported metrics during benchmark execution.

All other benchmark variables were held constant.

### Hypothesis

> Enabling observability will introduce a small but measurable runtime overhead due to additional metric collection performed during request processing.

The expected effects were:

- slightly lower peak throughput;
- modestly higher request latency;
- modestly higher CPU utilization;
- stable memory consumption;
- no significant impact on runtime stability or request correctness.

The result is consistent with the expected cost of performing additional metric updates during request processing.

# Analysis

## What the Results Mean

The benchmark demonstrates a consistent but modest performance regression when observability is enabled.

Under maximum throughput:

- throughput decreased by **3.45%**;
- mean latency increased by **3.60%**;
- transfer rate decreased by **3.39%**.

At the controlled rate of **500 requests/sec**:

- throughput remained effectively unchanged;
- mean latency increased by **2.42%**;
- P95 latency increased by **2.26%**;
- P99 latency increased by **3.73%**.

Instrumentation overhead becomes more visible when the proxy is driven toward saturation, while at the controlled workload the available processing capacity absorbs most of the additional work.

Supporting measurements show no evidence of a broader runtime regression: memory remained stable, goroutine counts returned to baseline, heap usage remained bounded, garbage collection remained stable, backend routing remained consistent, and request success remained at 100%.

## Threats to Validity

### Localhost Topology

The benchmark client, Torus, and backend servers executed on the same physical machine. Real deployments introduce network latency, routing overhead, and additional operating-system variability.

### Hardware Specificity

The reported absolute performance values apply to Hardware Profile H001. Different processors, cache hierarchies, memory configurations, and operating systems may produce different results.

### Workload Characteristics

The benchmark uses a simple HTTP GET workload with a 1 KB payload. Larger payloads, streaming responses, TLS termination, or computationally intensive backends may produce different relative instrumentation costs.

### Prometheus Scraping

The observability-enabled configuration includes both metric instrumentation and active Prometheus collection through `/metrics`.

Therefore, the reported overhead represents the operational cost of the complete observability configuration rather than instrumentation in isolation.

### Benchmark Scope

This benchmark does not evaluate:

- long-running stability;
- memory fragmentation;
- scalability across multiple machines;
- comparative performance against other reverse proxies;
- profiling of individual instrumentation functions.

# Conclusion

Torus observability introduces a **small but measurable runtime overhead**.

Under saturated load, enabling observability reduced average throughput by **3.45%** and increased mean request latency by **3.60%**. Under the controlled-rate Vegeta workload, throughput remained effectively unchanged while latency increased only marginally across the reported percentiles.

CPU utilization increased slightly, consistent with the additional work required to maintain Prometheus metrics. Memory utilization remained stable, while runtime observations showed bounded heap growth, predictable goroutine behaviour, stable allocation patterns, and stable garbage collection.

No evidence of runtime instability, resource exhaustion, routing problems, or instrumentation-induced correctness issues was observed.

The measured trade-off is therefore predictable and modest: Torus gains continuous operational visibility while giving up a small amount of peak processing capacity.

For deployments where monitoring and diagnostics are required, the benchmark supports enabling observability while recognizing its measurable cost under saturation.
