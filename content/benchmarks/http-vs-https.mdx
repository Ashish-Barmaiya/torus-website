# Benchmark-002: HTTP vs HTTPS Performance Evaluation

> **Status:** Complete

This benchmark measures the performance overhead introduced by TLS termination in Torus by comparing otherwise equivalent HTTP and HTTPS deployments under identical benchmark conditions.

The study evaluates throughput, latency, CPU utilization, memory consumption, and request correctness while holding the rest of the system constant.

## Executive Summary

Enabling TLS termination introduced a **measurable but modest performance cost**.

Under the saturated `wrk` workload, mean throughput decreased by **6.54%**, from **15,616.981 req/s** to **14,595.231 req/s**. Mean latency increased by **6.66%**, from **6.623 ms** to **7.064 ms**.

Under the controlled-rate `Vegeta` workload at **500 req/s**, throughput remained effectively unchanged while mean latency increased from **0.157 ms** to **0.172 ms**.

The resource measurements show that the primary cost of HTTPS was computational. Average CPU utilization increased by approximately **8.5%** under the controlled-rate workload and **21.5%** under peak throughput. Average resident memory increased by **20.4%** under Vegeta and **16.1%** under wrk.

Despite this overhead, both configurations maintained a **100% request success rate**, and CPU and memory behaviour remained bounded throughout the benchmark.

### Principal Findings

- Peak throughput decreased by approximately **6.5%** with TLS enabled.
- At **500 requests/sec**, throughput remained effectively unchanged.
- Mean latency increased modestly under both workloads.
- Tail latency increased consistently but remained bounded.
- CPU utilization increased, confirming additional cryptographic processing.
- Resident memory increased modestly but remained stable.
- No evidence of resource leaks or runtime instability was observed.
- All benchmark requests completed successfully.
- The primary `wrk` throughput measurements showed low run-to-run variability, with coefficients of variation of **2.46%** for HTTP and **2.49%** for HTTPS.

## Objective

The objective is to quantify the performance cost of TLS termination in Torus while isolating HTTPS as the only independent variable.

The benchmark answers four engineering questions:

1. How much throughput is lost when TLS termination is enabled?
2. How does HTTPS affect request latency?
3. What additional CPU and memory resources are required?
4. Is the measured overhead acceptable for the current implementation?

The resulting measurements establish a baseline against which future TLS, connection-management, memory-allocation, and request-processing optimizations can be evaluated.

---

## Hypothesis

> Enabling TLS termination will reduce maximum throughput and slightly increase request latency due to the additional cryptographic processing required by HTTPS. CPU utilization is expected to increase, while memory consumption should increase modestly because TLS introduces additional session state, cryptographic contexts, and temporary buffers.

Expected effects:

- lower peak throughput;
- higher request latency;
- higher CPU utilization;
- modestly higher memory usage;
- stable request correctness and runtime behaviour.

## Experimental Setup

The benchmark client, Torus, and both mock backends executed on the same physical machine.

```text
                    Benchmark Client
                     (wrk / Vegeta)
                           │
                     HTTP / HTTPS
                           │
                           ▼
                  ┌─────────────────┐
                  │      Torus      │
                  │ Reverse Proxy   │
                  └─────────────────┘
                           │
                    Round-Robin LB
                       │       │
                       ▼       ▼
                Mock Backend 1  Mock Backend 2
                localhost:3001  localhost:3002
```

Both backend servers executed identical binaries and returned identical responses.

### HTTP Scenario

- Torus accepted unencrypted HTTP connections.
- Requests were forwarded to the backends over HTTP.

### HTTPS Scenario

- Torus terminated TLS using the configured X.509 certificate.
- Requests were decrypted and then passed through the same routing and proxy pipeline.
- Backends continued to receive HTTP traffic.

The routing logic, load-balancing algorithm, backend implementation, and request-processing pipeline were unchanged between scenarios.

# Analysis

## Why Throughput Falls

The **6.54% reduction in peak throughput** is consistent with the additional work introduced by TLS termination.

HTTPS requires cryptographic processing that does not exist in the HTTP baseline, including:

- TLS handshake processing;
- session key establishment;
- symmetric encryption;
- symmetric decryption;
- message authentication;
- TLS protocol management.

The routing and backend pipeline remained unchanged, so the benchmark attributes the observed peak-throughput difference primarily to TLS processing.

The controlled-rate Vegeta workload provides an important qualification: at 500 req/s, throughput was effectively identical. This indicates that the TLS cost becomes operationally visible primarily as the proxy approaches saturation.

## Why Latency Increases

HTTPS increased latency in both workloads.

Under `wrk`, mean latency increased by **0.441 ms**. Under Vegeta, the absolute increase was only **0.015 ms**.

The percentage increase is larger for Vegeta because its HTTP baseline latency is extremely small. The absolute latency difference is therefore the more useful operational measure.

The consistent shift across the reported percentiles indicates a bounded processing cost rather than evidence of random latency spikes or architectural instability.

## Why CPU Is the Primary Cost

The CPU results show the clearest internal effect of enabling TLS.

At 500 req/s, average CPU utilization increased by approximately **8.5%**. Under peak throughput, average CPU utilization increased by approximately **21.5%**.

This is consistent with TLS moving additional work onto the proxy's CPU, particularly as request volume approaches the system's processing ceiling.

## Memory Overhead

HTTPS also increased average RSS:

- **+5.26 MB / +20.4%** under Vegeta;
- **+3.85 MB / +16.1%** under wrk.

The report attributes this additional memory to TLS session state, certificate structures, cryptographic contexts, and temporary encryption/decryption buffers.

Importantly, memory remained bounded throughout execution, with no evidence of progressive growth or resource exhaustion.

# Threats to Validity

The results should be interpreted within the scope of the documented experimental environment.

### Localhost Topology

The benchmark client, Torus, and both backends ran on the same physical machine. This removes network latency and packet loss from the measurement, which is useful for isolating proxy overhead but does not represent a distributed production topology.

### Hardware Specificity

All measurements were collected on a single hardware platform. Different CPUs, cache hierarchies, memory configurations, kernels, and cryptographic acceleration capabilities may produce different absolute results.

### Self-Signed Certificate

The HTTPS scenario used a locally generated self-signed certificate suitable for performance evaluation. Production certificate chains, cipher suites, and security policies may alter performance.

### Fixed Workload

The benchmark used a fixed request size, concurrency, duration, request rate, and two-backend topology. Larger payloads, long-lived connections, streaming, or higher concurrency may exhibit different characteristics.

### Benchmark Scope

This benchmark does not evaluate:

- TLS handshake scalability;
- HTTP/2;
- HTTP/3 / QUIC;
- session resumption;
- mutual TLS;
- large-payload performance;
- long-running stability;
- multi-node deployments.

### Environmental Variability

Repeated iterations reduce the effect of operating-system scheduling, background processes, CPU frequency scaling, and thermal behaviour, but cannot eliminate these factors entirely.

# Conclusion

TLS termination introduces a **predictable and manageable performance cost** in Torus.

At peak throughput:

- mean throughput decreased by **6.54%**;
- mean latency increased by **6.66%**;
- transfer rate decreased by **6.49%**.

At a controlled rate of 500 req/s:

- throughput remained effectively unchanged;
- mean latency increased by **9.65%** in relative terms, corresponding to only **0.015 ms** absolute increase;
- P95 latency increased by **0.020 ms**;
- P99 latency increased by **0.035 ms**.

The primary resource cost was CPU, with average utilization increasing by approximately **8.5%** under the controlled workload and **21.5%** near peak throughput. Average RSS increased modestly while remaining bounded.

Most importantly, both HTTP and HTTPS maintained a **100% request success rate**, with no evidence of memory leaks, resource exhaustion, or runtime instability.

The benchmark therefore establishes a reproducible HTTPS performance baseline for Torus. Future optimizations can now be evaluated quantitatively against these measurements.

# Future Work

The source benchmark identifies several areas for subsequent investigation:

- **TLS optimization:** configuration tuning, session resumption, keep-alive optimization, cipher-suite evaluation, and TLS 1.3-specific improvements.
- **Higher concurrency:** identify saturation point, throughput scaling, latency degradation, and scheduler behaviour.
- **HTTP/2 and HTTP/3:** compare newer transport protocols against the HTTP/1.1 baseline.
- **Larger payloads:** evaluate 10 KB, 100 KB, 1 MB, streaming, and large-upload workloads.
- **Comparative benchmarking:** evaluate Torus against NGINX, HAProxy, Envoy, Caddy, and Traefik using the same methodology.
- **Runtime profiling:** use Go pprof, perf, allocation profiles, and CPU flamegraphs to identify specific TLS-related bottlenecks.
